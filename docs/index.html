Why frequency is the wrong ranking

The most common command in any history is the one that costs nothing to run. Here it is ls, 22 times, and wrapping it saves nothing. Everything below is ranked by estimated time saved instead, under a model stated in full so it can be argued with:

  • typing rate 5.0 chars/sec (~60 wpm at 5 chars per word)
  • switch cost 0.80s per command boundary (recall, wait, decide; the weakest constant in the model)
  • setup cost 90s to write and install one suggestion

Is any of this real?

Two controls run on every report. Shuffling each session preserves how often every command was run and destroys only the order; a pattern that a shuffle can match as often as the real history is a coincidence of frequency and is dropped.

Over 20 shuffles the best pattern reached 4 occurrences, against 12 observed.

The second control is the session boundary itself. It is the density minimum between the two modes of the gap distribution (28s and 17783s), and the findings have to survive moving it:

Secrets

A history holds tokens, database URLs with passwords in them, ssh targets and internal hostnames. Redaction runs as the file is read, so no later stage ever holds an unredacted command, and the redactor is checked by a scanner that shares no code with it and reads bytes rather than text, so one NUL byte cannot blind it to a whole file.

This fixture is secret-free by construction, and the redactor fired 0 times on it. Redaction is exercised against a separate fixture of twenty credential-carrying commands, where the test compares against the exact values planted rather than asking whether the output looks clean.
